# Verified implementation decisions

Researched 2026-11-13 against official sources, before implementation. The runtime versions are pinned in pnpm-lock.yaml. The official SDK v2.4.0 supports MCP 2026-07-28 plus a stateless compatibility path for 2025 clients. No Agents SDK is needed because the official SDK exposes a native Workers `{ fetch }` handler.

## Intervals.icu

- [Official API UI](https://intervals.icu/api-docs.html) and [OpenAPI JSON](https://intervals.icu/api/v1/docs): `APIKey` security scheme is HTTP Basic, username `API_KEY`, password the personal key. Athlete ID `0` resolves to the key owner ([maintainer API guide](https://forum.intervals.icu/t/api-access-to-intervals-icu/609)).
- Selected exact GET operations and source checksum are retained in [api-reference.json](api-reference.json). `{ext}`/`{format}` are empty for JSON, not literal suffixes. The code uses no upstream mutation endpoints.
- Activities use `oldest`/`newest` local dates or timestamps, a limit, and a field selection. Events and wellness use inclusive local date ranges. No cursor/offset pagination is documented for these operations. Bounded queries use sentinel limits (1001 activities, 301 events) and refuse incomplete aggregates. Maximum range is 90 days, no backfill loop.
- Details use `GET /api/v1/activity/{id}?intervals=false`; optional intervals use `GET /api/v1/activity/{id}/intervals` and the `icu_intervals` collection. These are Intervals analysis intervals and are not guaranteed to be original device laps. No streams are fetched.
- `Wellness` documents `ctl`, `atl`, `ctlLoad`, `atlLoad`, `rampRate`. Preserve all five. No daily source `tsb`/`form` property is documented. `computed_form` is explicitly same-day `ctl - atl`, with `source_form_tsb: null`. This does not reproduce a percentage chart setting or a convention using previous-day values. Source CTL/ATL are never recomputed. [Maintainer confirmation of fitness in wellness](https://forum.intervals.icu/t/ios-app-fitnessfatigue-for-intervals-icu-data/11186).
- Activities and calendar events are separate collections; `Activity.paired_event_id` links a completed activity to an event. An unpaired `WORKOUT` remains planned, even in the past; other categories remain `calendar_event`. Race/note dates never prove completion.
- Distance is meters, speed m/s, duration seconds, weight kg; pace is derived as `1000 / average_speed`. Intervals running cadence uses rpm; preserve it and explicitly derive running steps/minute as twice rpm ([maintainer discussion](https://forum.intervals.icu/t/additional-or-different-units/4526)).
- Subjective wellness/readiness score scales and HRV measurement methods/units are not fully defined in the OpenAPI schema. Preserve source numbers and call out uncertainty. No arbitrary conversion or recovery conclusion.
- The profile response can contain `icu_api_key`. Zod whitelist parsing strips it, contact information, provider tokens, and all unrequested settings before normalization.
- Strava-origin records can be restricted to stubs according to the documented activity endpoints. They remain visibly incomplete in recent lists; they block aggregates that would otherwise undercount. COROS synchronization freshness remains external.
- The maintainer guide documents rate-limit headers, 429 with Retry-After, and an additional per-IP limit. Client honors short retry delays and returns long delays without retrying prematurely; it does not rely on fixed quota numbers.

## MCP and Cloudflare

- [MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28), [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http), [tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization).
- [Official TypeScript SDK web-standard handler](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/serving/web-standard.md): per-request server factory, structured outputs, schema validation. Native fetch avoids a Node HTTP adapter and unnecessary framework. Both current and legacy protocol paths are independently tested. Legacy GET/DELETE session operations return 405; there is no resumable session or unsolicited stream.
- [Cloudflare stateless MCP](https://developers.cloudflare.com/agents/model-context-protocol/apis/handler-api/) and [authorization](https://developers.cloudflare.com/agents/model-context-protocol/protocol/authorization/): OAuthAuthorizationServer and OAuthResourceServer can share one Worker. Only auth uses KV. No Durable Object or athlete database is needed.
- Native Workers fetch supports `manual`, not `error`, redirect mode; reject redirect statuses without following them ([Request API](https://developers.cloudflare.com/workers/runtime-apis/request/)). Bind injected native fetch to `globalThis` before storing it on the API client to avoid Workers illegal-invocation errors. Both behaviors were checked in workerd.
- [Workers best practices](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/), [secrets](https://developers.cloudflare.com/workers/configuration/secrets/), [Wrangler commands](https://developers.cloudflare.com/workers/wrangler/commands/). Generated Env types, nodejs_compat, bounded body reads, no raw request logs.
- [Cloudflare OAuth provider](https://github.com/cloudflare/workers-oauth-provider), [consent helpers](https://github.com/cloudflare/workers-oauth-provider/blob/main/docs/consent-page.md), [upstream sign-in](https://github.com/cloudflare/workers-oauth-provider/blob/main/docs/upstream-sign-in.md), [resource validation](https://github.com/cloudflare/workers-oauth-provider/blob/main/docs/resource-servers.md). Version 1.2.4 owns PKCE, browser-bound consent and state, encrypted auth state, opaque tokens, audience binding, expiry, refresh rotation and revocation. Scope enforcement is explicitly the application's responsibility.
- `global_fetch_strictly_public` is mandatory for safe CIMD fetching; it is configured and checked in the actual runtime test. DCR is disabled by default; owners can explicitly enable `/oauth/register` for legacy clients. Registration does not authorize private access. Current MCP guidance prefers CIMD for new implementations. A malicious client metadata URL still cannot obtain tokens without consent and the allowed identity.
- [GitHub OAuth app flow](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps) supports S256; [authenticated identity](https://docs.github.com/en/rest/users/users#get-the-authenticated-user) returns numeric ID without private-profile scopes. Tokens are used for identity once, discarded, and never forwarded as MCP credentials. The immutable ID is checked at issuance and every MCP request.

## ChatGPT

- [Build MCP servers](https://developers.openai.com/api/docs/mcp), [plugin authentication](https://developers.openai.com/plugins/build/auth), [custom MCP setup](https://developers.openai.com/api/docs/guides/custom-mcp-server), [Help Center](https://help.openai.com/en/articles/12584461-connecting-custom-mcp-servers-in-chatgpt).
- ChatGPT supports OAuth authorization-code + S256, protected resource discovery and CIMD (public `none` or `private_key_jwt` client authentication). Custom API-key headers and client-credentials grants are not a supported replacement. This server uses CIMD with the provider's accepted methods; no static client ID or client secret is needed in ChatGPT.
- The authorization server advertises RFC 9207 issuer identification and echoes `iss`; use the exact CIMD document and callback displayed by ChatGPT. A current conforming setup normally uses `https://chatgpt.com/oauth/client.json` and `https://chatgpt.com/connector_platform_oauth_redirect`; do not hardcode a possibly different callback into application logic.
- Local Inspector success demonstrates protocol compatibility only. Deployed OAuth browser flow, real Intervals credentials, and a ChatGPT plugin installation are distinct acceptance checks and require separate evidence.

## Open-source self-hosting update

One independent instance per owner supersedes the earlier personal-project framing. Owners configure their own upstream Secrets, public origin, GitHub OAuth app, immutable owner ID and isolated OAuth KV namespace. Application source has no owner identity or deployment URL. Intervals field normalization is in the upstream adapter; portable domain models/aggregation are typechecked without Workers types.

Rechecked the official SDK registry: the installed `@modelcontextprotocol/server` 2.4.0 remains current at verification. Rechecked current OpenAI authentication documentation: CIMD, optional DCR, S256, resource/issuer validation and authorization-code OAuth remain supported. This verifies documented compatibility, not a live ChatGPT installation.

[Cloudflare registration reference](https://github.com/cloudflare/workers-oauth-provider/blob/main/docs/authorization-server.md) documents opt-in DCR and persistent client registration. The implementation keeps CIMD as default and DCR configurable, preserving the same consent/owner checks. Exact browser origins are owner settings rather than client-vendor assumptions.

CI uses official `actions/checkout` and `actions/setup-node` v6 release commits resolved from their upstream Git tags. Both use the Node.js 24 action runtime; the application matrix tests Node.js 22 and 24. CI never handles athlete credentials or deploys.
